# 状态机 · 【遗留问题】与返工规则

这是干什么的：提词器新增功能的规则正本。代码按本文件实现；改规则先改本文件，再改代码。

## 1 她的原话（逐字，不改写）

> 【遗留问题】是新的、未完成的、ai层级。完成状态变为【已解决】，在【已完成】层级。
> 回答前，视为【ai待办】。
> 回答后的文件，读取优先度介于【待办】和【ai待办】之间。
> 如回答后，ai已读取、且未解决的同时、要新增【遗留问题】，只能另开新文件，不能修改已经被回答的文件。
> 【已解决】视为【ai新增】，和【ai转正】视为【已完成】做区分。
> 依旧适用【返工】后的所有都变【已完成】。
> 【遗留问题】内的回答也是原始需求（代码自动记，用户确认）。

## 2 返工口径纠正（她 2026-11-06 00:29，逐字）

> 「返工后变成已失效」的意思是被【返工完成】顶替的【完成】变成【已失效】。其他需求不被静默顶替

两条规则**针对不同对象、同时生效**，不是新旧互斥、旧话不作废：

| 对象 | 返工后 | 依据 |
| --- | --- | --- |
| 【返工完成】这条新结果 | 【已完成】 | 本轮新话「返工后所有都变已完成」 |
| 被它顶替的**那条旧【完成】** | 【已失效】 | 原始需求 txt 旧话 |
| 其余所有需求 | 一个都不动（不静默顶替） | 本轮补充原话 |

## 3 代码里的对应

| 规则 | 落点 |
| --- | --- |
| 回答前 = 【ai待办】 | `app/backend/issues.js` `add()` 的 `status: "ai_todo"` |
| 回答 = 原始需求，代码自动记、用户确认 | `answer()` 写 `{id}-回答-{n}.md`，`confirm()` 才变 `resolved` |
| 回答后的文件不改；新增只另开新文件 | `answer()` 按序号找空文件名，`add()` 也只用新 id |
| 读取优先度 待办 > 回答后文件 > ai待办 | `exportText()` 三段顺序；前端「生成本轮需求」按钮 |
| 【已解决】= 【ai新增】 | `confirm()` 的 `layer: "ai_new"` |
| 【ai转正】= 【已完成】，与前者区分 | `promote()` 的 `layer: "ai_promoted"` |
| 返工：新结果已完成／旧完成已失效／其他不动 | `rework()` 只改被顶替的一条 + 另开新条目 |
